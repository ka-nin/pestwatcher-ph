====================================================================
PESTWATCHER PH — HOW TO RUN EVERYTHING (macOS/Linux + Windows)
====================================================================

Run these in order. Steps marked [ONE-TIME] only need to be done once
per machine (or once after a fresh git clone). Steps marked [EVERY
TIME] are what you run each time you sit down to work.

Prerequisites (both OS): Node.js 24.x, Python 3.11-3.13, Docker
Desktop, Git. Docker Desktop must be OPEN/RUNNING before any docker
command. (TensorFlow 2.21 in requirements.txt runs on 3.13 — the dev
machine is on 3.13.13 — so an earlier note demanding 3.11 was wrong.
Avoid 3.14+, which TensorFlow has no wheels for yet.)


--------------------------------------------------------------------
1. [ONE-TIME] CLONE AND INSTALL
--------------------------------------------------------------------
Same commands on both OS. Run "npm install" from the repo ROOT — it
is an npm workspace and installs admin-web + user-mobile in one go.

git clone https://github.com/ka-nin/pestwatcher-ph.git
cd pestwatcher-ph
npm install


--------------------------------------------------------------------
2. [ONE-TIME] PYTHON BACKEND SETUP
--------------------------------------------------------------------

--- macOS / Linux ---
cd server-python
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
cd ..

--- Windows ---
cd server-python
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
cd ..

(pip install is large — TensorFlow + SHAP — so expect a few minutes.)

NOTE — ResNet image model: ml/weights/*/resnet50_*.keras is gitignored
(too big for GitHub), so a fresh clone does NOT have it. Get the two
files (resnet50_bph.keras, resnet50_rsb.keras) from a teammate and put
them in server-python/ml/weights/bph/ and .../rsb/. Without them,
photo-based pest detection will fail; the BiLSTM forecast files ARE
in git and work as-is.


--------------------------------------------------------------------
3. [ONE-TIME] FRONTEND ENV FILES
--------------------------------------------------------------------
Both frontends talk to the backend over plain HTTP on port 8000.
The .env.example files already contain the right value
(VITE_API_URL=http://localhost:8000), so just copy them.
(No custom HTTPS certificate is needed anymore — the old certs/ step
and the HTTPS backend on port 8443 were removed.)

--- macOS / Linux ---
cp admin-web/.env.example admin-web/.env
cp user-mobile/.env.example user-mobile/.env

--- Windows ---
copy admin-web\.env.example admin-web\.env
copy user-mobile\.env.example user-mobile\.env


--------------------------------------------------------------------
4. [EVERY TIME] START THE DATABASE
--------------------------------------------------------------------
Same command on both OS. Run from the repo root. Docker Desktop must
already be running.

docker compose up -d

This starts:
  - PostgreSQL   -> localhost:5432
  - pgAdmin (DB web UI) -> http://localhost:8080
    Log in to pgAdmin itself first:
      Email    = admin@pestwatcher.dev
      Password = pestwatcher_dev_only
    The server "PestWatcher (local Docker)" is already registered in the
    left tree; expand it and enter the DATABASE password when asked:
      Password = pestwatcher_dev_only   (user "pestwatcher", db "pestwatcher")
    Tables live under: Databases > pestwatcher > Schemas > public > Tables


--------------------------------------------------------------------
5. [EVERY TIME] START THE BACKEND
--------------------------------------------------------------------
One backend serves BOTH frontends (plain HTTP, port 8000).

--- macOS / Linux ---
cd server-python
source .venv/bin/activate
uvicorn app.main:app --reload --port 8000

--- Windows ---
cd server-python
.venv\Scripts\activate
uvicorn app.main:app --reload --port 8000

--- Windows shortcut (no activate needed; uses .venv\Scripts\uvicorn) ---
npm run dev --workspace=server-python        (from repo root)
   or:  cd server-python && npm run dev

Check it: http://localhost:8000/api/health
API docs: http://localhost:8000/docs

SMS advisories default to SIMULATION (SMS_PROVIDER=console in
server-python/.env), so the "SMS Advisory" tab in admin-web works
out of the box with no phone and no SIM — messages are recorded in
the outbox and printed to the backend log, but nothing is actually
sent. See section 7 to send real texts.


--------------------------------------------------------------------
6. [EVERY TIME] START THE FRONTENDS
--------------------------------------------------------------------
Same commands on both OS. Use a separate terminal for each.

--- admin-web (LGU dashboard + SuperAdmin console) ---
cd admin-web
npm run dev
-> http://localhost:5173

--- user-mobile (normal mode, real browser tab, camera works) ---
cd user-mobile
npm run dev
-> https://localhost:5174
   (self-signed cert from @vitejs/plugin-basic-ssl — click through
   the "not secure" warning once: Advanced -> Proceed. This is only
   for the frontend; the backend stays on plain http://localhost:8000
   and that works fine from a localhost page.)

--- user-mobile (embedded webview / VS Code mobile-view preview) ---
cd user-mobile
npm run dev:preview
-> http://localhost:5174   (plain HTTP, no cert warning, no camera)

--- Testing on a real phone (same Wi-Fi) ---
The dev server is exposed on your LAN. On the phone, "localhost"
means the phone itself, so:
  1. Find your computer's LAN IP (macOS/Linux: ifconfig / ip a;
     Windows: ipconfig), e.g. 192.168.1.138.
  2. In user-mobile/.env set  VITE_API_URL=http://192.168.1.138:8000
  3. In server-python/.env add https://192.168.1.138:5174 to
     CORS_ORIGINS, then restart the backend and "npm run dev".
  4. Start the backend so it's reachable from the LAN:
       uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
  5. Open https://192.168.1.138:5174 on the phone.
Revert step 2 when you're back to desktop-only testing.


--------------------------------------------------------------------
7. [OPTIONAL] DEMO DATA, TESTS, BUILDS, RETRAINING
--------------------------------------------------------------------
Python commands run from server-python/ with the venv active (on
Windows without activating, use .venv\Scripts\python.exe in place of
"python"). Postgres must be up where noted.

--- Seed mock farmer reports (Nueva Ecija demo data) ---
python -m scripts.seed_mock_reports            # insert (idempotent)
python -m scripts.seed_mock_reports --remove   # delete all mock rows
(needs Postgres; dates are relative to today so they stay "recent")

--- Backend tests ---
python -m pytest tests/ -v
(test_inference.py hits the real dev database and runs a live
forecast, so start Postgres first: docker compose up -d)

--- Lint / production builds (from repo root) ---
npm run lint  --workspace=admin-web
npm run lint  --workspace=user-mobile
npm run build --workspace=admin-web
npm run build --workspace=user-mobile

--- Retrain the BiLSTM forecast model (details: server-python/README.md) ---
python -m ml.datasets.cleaning.clean_timeseries
python -m ml.bilstm.ingest_reports     # optional; folds verified reports
                                       # into training data (needs DB)
python -m ml.bilstm.build_sequences
python -m ml.bilstm.train --pest BPH
python -m ml.bilstm.train --pest RSB
python -m ml.validity_test             # pass/fail check on both pests (needs DB)
Extras: python -m ml.bilstm.export_insights --pest BPH   (or RSB)
        python -m ml.explainability.shap_report --pest BPH   (or RSB)

--- Thesis evidence: the numbers that fill Table 3 ---
RQ1.1.2 — ETL Low/Medium/High agreement for the model already on disk
(no retraining, leaves the weights and the cited R2/RMSE/MAE alone):
python -m ml.bilstm.etl_metrics

High-risk band recall — the plain model never predicts "High" (MSE on a
skewed target collapses toward the mean). These two flags counter that;
--tag keeps the experiment away from the deployed weights:
python -m ml.bilstm.train --pest BPH --log-target --balance-bands --tag logw
python -m ml.bilstm.train --pest RSB --log-target --balance-bands --tag logw

Lagged verified-observation features (simulated reporting cadence, so the
feature is as sparse in training as it is in production):
python -m ml.bilstm.build_sequences --features lagged
python -m ml.bilstm.train --pest BPH --features lagged
python -m ml.bilstm.train --pest RSB --features lagged

RQ2 + RQ3 — engineered vs raw climate features, 5-fold expanding-window
time-series CV, then a paired t-test per metric (Wilcoxon when the paired
differences fail Shapiro-Wilk). Build both feature sets first:
python -m ml.bilstm.build_sequences                  # engineered
python -m ml.bilstm.build_sequences --features raw   # the control
python -m ml.bilstm.compare_features --pest BPH
python -m ml.bilstm.compare_features --pest RSB
(trains 10 models per pest — expect this to run for a while. Results go to
ml/weights/{pest}/bilstm_{pest}_feature_comparison.json)

--- SMS advisories: real texts instead of simulation ---
The LGU technologist sends these from admin-web > "SMS Advisory".
Sending is always manual; the system never texts farmers on its own.

Simulation (default, nothing leaves the server) — server-python/.env:
SMS_PROVIDER=console

Live, via an Android handset acting as the gateway:
  1. Install "SMS Gateway for Android" (https://docs.sms-gate.app) and
     turn on LOCAL SERVER mode. Do NOT use Cloud mode — Cloud is the one
     that asks you to register a device, and it is not needed here.
     Tap the "Offline" button at the bottom so it reads "Online".
     The Local Server panel then shows the phone's IP, a username and
     a password.
  2. Grant the app the SMS permission, and set its battery usage to
     UNRESTRICTED. Android Doze freezes the app otherwise: the phone
     still answers ping and TCP:8080 still accepts, but every HTTP
     request times out. On Xiaomi/Oppo/Realme/Vivo also enable Autostart.
  3. The SIM must have ACTIVE SERVICE AND LOAD. SMS rides the cellular
     network; Wi-Fi/Tailscale only carries the request to the app.
     A phone showing "No Service" cannot send or receive.
  4. In server-python/.env:
     SMS_PROVIDER=android_gateway
     SMS_GATEWAY_URL=http://<phone-ip>:8080
     SMS_GATEWAY_USERNAME=<from the app>
     SMS_GATEWAY_PASSWORD=<from the app>
     SMS_DEFAULT_COUNTRY_CODE=+63
     (If the phone is on Tailscale, use its 100.x address so the gateway
     also works off the local Wi-Fi.)
  5. Restart the backend. The banner at the top of the SMS Advisory tab
     turns green when the handset answers.

Test the gateway directly before trusting the UI:
curl -X POST -u USER:PASS -H "Content-Type: application/json" \
  -d '{"textMessage":{"text":"test"},"phoneNumbers":["+639XXXXXXXXX"]}' \
  http://<phone-ip>:8080/message

Clear the outbox before a demo (needs Postgres):
docker exec pestwatcher-postgres psql -U pestwatcher -d pestwatcher \
  -c "delete from sms_messages;"

Farmers only appear as pickable recipients once they have a phone
number on file (farmer_users.phone). Until then, type the number
straight into the compose box.


--- Retrain the ResNet image model (needs the image dataset) ---
python -m ml.resnet.prepare_dataset --pest BPH   (or RSB)
python -m ml.resnet.train --pest BPH             (or RSB)

9. STOPPING EVERYTHING
--------------------------------------------------------------------

--- macOS / Linux: stop the dev servers + backend ---
pkill -f "vite"
pkill -f "uvicorn"

--- Windows: stop the dev servers + backend ---
Close the terminal windows/tabs running them (Ctrl+C), or:
    taskkill /F /IM node.exe
    taskkill /F /IM python.exe
(these kill ALL Node/Python processes system-wide — fine if this is
the only project you're running, otherwise close the specific
terminal windows instead)

--- Both OS: stop the database (Postgres + pgAdmin) ---
docker compose down
(stops and removes the containers; your data is kept in the Docker
volume. Only add -v — "docker compose down -v" — if you also want to
permanently delete the database contents.)


--------------------------------------------------------------------
10. TROUBLESHOOTING
--------------------------------------------------------------------
- "Failed to fetch" in user-mobile / admin-web
    -> Is the backend running on port 8000? Check
       http://localhost:8000/api/health. Is VITE_API_URL in the
       frontend's .env exactly http://localhost:8000 (restart the
       Vite server after editing .env)?

- Browser shows a CORS error
    -> The page's origin must be listed in CORS_ORIGINS in
       server-python/.env (restart the backend after editing). If
       your .env predates the latest .env.example, compare the two.

- Backend can't connect to the database
    -> Is Docker Desktop open? Did you run "docker compose up -d"?
       DATABASE_URL in server-python/.env should match
       .env.example (localhost:5432, user/db "pestwatcher").

- Backend crashes on startup with ModuleNotFoundError
    -> Venv not active, or requirements changed since you last
       installed. Activate .venv and rerun
       "pip install -r requirements.txt".

- Backend crashes on startup mentioning a .keras / model file
    -> Missing ResNet weights — see the NOTE in section 2.

- pip install fails on tensorflow
    -> You're on a Python TensorFlow has no wheels for (3.14+ is too
       new; 3.11-3.13 are fine). Check "python --version" and recreate
       the venv with a supported interpreter.

- admin-web and user-mobile open the same URL
    -> Check admin-web/vite.config.ts has port: 5173 and
       user-mobile/vite.config.js has port: 5174.

- Frontend fails with missing-package errors after pulling
    -> Rerun "npm install" from the repo ROOT.

- Dashboards show no farmer reports
    -> Seed demo data: python -m scripts.seed_mock_reports (section 7).

- Need to wipe and re-seed the database from scratch
    -> docker compose down -v && docker compose up -d
       (deletes all local DB data, backend recreates + reseeds on
       next startup)

- pgAdmin can't connect to the server
    -> Inside the pre-registered server the Host must be "postgres"
       (the Docker service name), NOT "localhost" — pgAdmin runs in its
       own container, where "localhost" means pgAdmin itself.
